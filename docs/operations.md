# Запуск, сопровождение и приёмка

## Настройка режима наблюдения

Скопируйте пример конфигурации и укажите подтверждённые проекты. Для существующего реестра мониторинга цен настройте `price_monitor_registry` и `price_monitor_id`. Храните конфигурацию и базу вне Git. Для Google используйте отдельную учётную запись с правами чтения только на утверждённые таблицы. Доступы к Avito и Telegram для сухого прогона не нужны.

На новом проекте запустите `check --project ИД` в режиме `draft`. Сверьте схему, отсутствие конфликтующих ключей, форматы цен и источники для каждой товарной вкладки. Задайте `coverage_targets`, чтобы в сводке появились заполненные строки вне правил. Технический `Id` и номер объявления задаются разными полями. Переведите проверенный проект в `monitoring`. Остановка проекта выполняется через `paused`.

Цена принимается как отсутствующая, только если ячейка действительно пуста. Ноль, текст, ошибка формулы и пустой результат формулы требуют отдельного решения. Удалённую или несопоставленную строку сервис относит к диагностике. Проект не отмечается полностью проверенным, пока остаётся эта диагностика.

## Как пройти сценарий с Id

1. Получите полную сверку и сохраните её как базовый снимок. Укажите утверждённые `removal_limits` с абсолютными пределами `max_candidates`, `max_newly_empty` и `max_lost_matches`.
2. Выполните `plan-removals --project ИД`. План укажет кандидатов и причины запрета. При превышении пределов блокировка сохраняется в базе. После проверки причины можно выполнить `release-removal-hold --project ИД --reason '…'`. Если причина осталась, блокировка сработает снова.
3. Для репетиции передайте локальный снимок в `--fixture` и запустите `rehearse-removals --project ИД --save-fixture НОВЫЙ.json`. Команда применяет проверенный план только к новому локальному файлу. Для испытания одной ячейки есть `pilot`. При неизвестном результате записи сервис оставляет `WRITE_STARTED` и не повторяет очистку автоматически.
4. Проверьте операцию командой `registry --project ИД`. В истории находятся исходное значение и тип ячейки, привязка к позиции, состояние операции, дата и причина.
5. Выполните `confirm-feed --project ИД --operation UUID --before ДО.xml --after ПОСЛЕ.xml`. Если строка осталась без `Id`, статус останется `WAITING_FEED_CONFIRMATION`. Для доказанного исключения строки добавляются хеши обоих файлов и статус `WAITING_AVITO_CONFIRMATION`. При неуникальном заголовке укажите устойчивые поля с `--match-field`. Пустой или несопоставимый фид не проходит проверку.
6. Для чтения активности через существующий монитор цен предусмотрен `bridge/observe_active.py`. Запускайте его в окружении действующего монитора, добавив каталог с его модулем `app` в `PYTHONPATH`, с `--autoload-book ИД --marketplace-id НОМЕР`. Он читает только список активных объявлений и выдаёт JSON для `record-avito --project ИД --operation UUID --evidence ФАЙЛ.json`. Отсутствие в активных хранится как `NOT_SEEN`. Для подтверждения снятия необходим явный статус из карточки или отчёта, относящийся к тому же объявлению и полученный после проверки XML.
7. Когда цена вернулась, оператор вручную вставляет прежний `Id`. Команда `observe-restore --project ИД --operation UUID` подтверждает точное значение и положительную цену. Резерв остаётся в истории. Автоматическое создание или восстановление `Id` не включено.

Проверка на локальном XML показывает поведение выбранного правила. Команды `confirm-feed` и `record-avito` также доступны для диагностики старых операций.

## Автоматические операции с Id

Для проекта, допущенного к записи после проверки на изолированном контуре, настройте `removal_confirmation: avito_status`, `avito_credential_prefix`, согласованные `removal_limits` и `auto_remove: true`. Используйте Sheets API, дайте сервисному аккаунту права редактора на согласованную автозагрузку и права читателя на прайс. В защищённом окружении укажите разрешённые ID автозагрузок через пробел в `AVITO_MONITOR_WRITABLE_BOOKS` и передайте секреты аккаунта в переменных `<PREFIX>_CLIENT_ID` и `<PREFIX>_CLIENT_SECRET`.

По расписанию служба строит план, сверяет технический `Id` и активность объявления через API, резервирует ячейку, повторно читает источник и очищает только совпавшее значение в согласованном диапазоне. В следующих циклах она получает статус конкретного номера. Операция считается подтверждённой после явного статуса снятия. Коды ошибок и неопределённые ответы оставляют операцию на проверке. При неизвестном результате записи служба сверяет ячейку на следующем цикле без повтора очистки. После возвращения цены прежний `Id` доступен в журнале, сотрудник возвращает его по ТЗ, служба сама регистрирует восстановление при очередной сверке.

## Сводка и планировщик

Включите `sync` для проектов с постоянным мониторингом. В Google Cloud включите Google Drive API и Google Sheets API, на сервере настройте Application Default Credentials. Дайте сервисному аккаунту права читателя на прайс и автозагрузку, для общих дисков также доступ к нужному диску. Служба обнаруживает общий диск по метаданным файла. При необходимости его ID можно задать явно в `sync.shared_drive_ids`. Даты запуска, источники и аккаунты Avito задаются в реестре проектов.

```json
{
  "report_timezone": "Europe/Moscow",
  "telegram_enabled": false,
  "sync": {},
  "schedule": {
    "check_every_minutes": 60,
    "report_time": "08:00",
    "report_window_minutes": 10,
    "report_weekdays": [0, 1, 2, 3, 4, 5, 6]
  }
}
```

`tick` запускается раз в минуту. Он сохраняет позицию в журнале Drive в одной транзакции с постановкой обновлений в очередь. При изменении прайса используется сохранённая автозагрузка этого проекта. Проведённые сверки, очередь и резервы Id переживают перезапуск. Стартовые и контрольные загрузки выполняются небольшими группами. Один затруднённый проект повторяется по собственному расписанию.

По умолчанию контрольный обход с Drive API проводится раз в сутки. Прайсы с формулами в сопоставленных позициях отдельно перечитываются раз в час. Для доступных по ссылке XLSX-копий используется собственная часовая сверка двух файлов. Эти интервалы управляются `sync.audit_every_minutes`, `sync.formula_every_minutes` и `sync.export_every_minutes`. За запуск обрабатывается до 6 проектов и используется до 40 запросов Sheets API. Ограничения можно менять через `sync.max_projects_per_tick` и `sync.max_sheet_requests_per_tick` с учётом квот Google. Команда `status` показывает отметки загрузки файлов и текущие задания.

Сводка фиксируется отдельным таймером один раз на дату, использует согласованный снимок базы и отмечает проекты с просроченными данными, ошибками или ожидающим обновлением. Дата запуска считается первым календарным днём. Проект стартовавший 20 ноября, попадёт в сводку с 30 ноября при стандартном правиле 10 дней. Опция `notify_during_grace` управляет оперативными предупреждениями в этот период, `notifications_enabled` позволяет приостановить их для проекта. В общем чате выводятся два раздела с количеством позиций по категориям для каждого проекта. Длинную сводку бот делит на пронумерованные части в том же чате. Для просмотра отдельных строк используйте `report --details`.

Пример systemd в `deploy/` требует пользователя `avito-monitor`, установленной виртуальной среды и локального конфигурационного файла. Один таймер вызывает `tick` для синхронизации, второй вызывает `dispatch` для сводки и доставки. До подключения Telegram используйте `telegram_enabled: false`.

При условии `telegram_enabled: true` задайте один `TELEGRAM_CHAT_ID` и токен отдельного бота в защищённом окружении. Команда `dispatch` сначала обрабатывает сводку за текущую дату, затем оперативные события. Для ручной проверки отдельной очереди предусмотрены `deliver` и `deliver --daily`. При занятой базе следующий запуск таймера повторит обработку. Если результат отправки неизвестен, сверяйте чат, прежде чем повторять вручную. Доставка из локального снимка запрещена. Перед обновлением остановите таймер, сделайте резерв SQLite, проверьте новую версию на снимке, затем верните таймер. Для отката остановите новый монитор и верните предыдущий код и совместимую базу. Перенос цен остаётся отдельной службой.

## Что проверено на Гатчине

- Ручной запуск действующего переноса на контрольной копии безопасно сверил 278 цен. В журнале 0 ошибок и 0 необходимых обновлений.
- Автоматическое сопоставление на копиях дало 768 точных пар и 103 позиции с ценой и пустым `Id`. Подтверждённых кандидатов к снятию нет.
- 318 строк без точной пары вынесены в диагностику. Два смарт-часа Samsung с заполненным `Id` не нашлись в прайсе.
- На одной позиции Apple Watch в копии проверены сохранение точного ID, очистка, повторное чтение и восстановление исходных значений. Действующий монитор подтвердил активность объявления в рамках безопасного теста.
- В локальных XML воспроизведены два варианта поведения. Без правила исключения запись осталась без тега `Id`. С явным фильтром пропала только выбранная запись. В ранее сохранённом рабочем XML есть 155 записей телефонов с ценой и без тега `Id`.
- Совместимость переноса цен проверялась на копии, а существующий монитор цен прошёл свою штатную проверку из 52 тестов. Новая сборка прошла собственные тесты, включая одновременный доступ, возврат ID, задержки, частичные ошибки, согласование расписания и повторную доставку без дублей через подставной отправитель.
- Нагрузочный тест с 300 моделируемыми проектами и 30 000 позиций проверяет загрузку по очереди, продолжение после перезапуска, чтение одного изменившегося файла и формирование утренней сводки без обращений к таблицам.

Серверный пилот использует только чтение копий Гатчины и общий тестовый чат. Для перевода на рабочие таблицы нужны утверждённые проекты, их даты и сверенные правила сопоставления. Для активации очистки отдельно нужны подтверждённые пределы, права записи и тест, в котором изменение действительно привело к снятию разрешённого объявления на площадке.
